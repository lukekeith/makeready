## Root cause

- **A — Confirmed. A deployed fix that does not work.** This is the same defect as ticket
  **`12628642531`**, fixed by commit **`ff7fb78`** (2026-07-25) and left at
  `resolved-pending-verify`. That dossier's "Remaining check for the user" reads: *"open a lesson
  Preview → exegesis step, background the app, return, and confirm the scripture is no longer
  clipped and the `‹ Done ›` toolbar pins to the real bottom with no empty gap."* **shot-4 is that
  check failing** — the `‹ Done ›` bar is stranded mid-screen with exactly the empty gap the fix
  was meant to remove.

  **The fix is genuinely live.** I fetched the production build manifest and the deployed
  `lesson-island` bundle from `app.makeready.org` and confirmed all four markers are present
  (`lesson-vh`, `orientationchange`, `pageshow`, `visibilitychange`). So this is **not** an
  undeployed fix — the mitigation is insufficient.

  *Leading hypothesis (needs runtime confirmation):* `syncViewportHeight`
  (`lesson-island.vue:99-101`) pins `--lesson-vh` to **`window.innerHeight`** — the *layout*
  viewport. shot-4 shows a **focused web input with the iOS form-assistant bar raised**, which
  shrinks the *visual* viewport while leaving `window.innerHeight` unchanged. The file never
  references `window.visualViewport` (verified by grep across the whole lesson-island directory),
  so a keyboard/accessory-driven collapse is invisible to the current listener set — which
  explains why `pageshow`/`visibilitychange` firing correctly still leaves the layout wrong.
  A secondary possibility is that returning from the iOS **share sheet** never backgrounds the
  app, so neither resume event fires at all.

- **C — Confirmed same class, step never covered.** Identical collapse signature with **no
  keyboard involved** (shot-2), which means the visual-viewport hypothesis above cannot be the
  whole story for C. `ff7fb78`'s own resolution log claims only that *"`read-step.vue` benefits
  for free via the shared var"* — `youtube-step.vue` was never considered. The embedded YouTube
  iframe is a plausible additional factor (an iframe that reports its own dimensions can hold the
  page at a stale height independent of `--lesson-vh`).

- **B — Confirmed, code-level.** The note sheet is sized from screen geometry with **no keyboard
  inset anywhere in the chain**: `expandedSheetHeight = max(560, Screen.bounds.height −
  topSafeAreaInset − 40)` (`:1355-1357`) → `editorContentHeight = expandedSheetHeight −
  bottomSafeAreaInset − 76` (`:1347-1349`) → `noteEditorHeight = max(220, editorContentHeight −
  152)` (`:1351-1353`). The `MarkdownEditor` is then given a **fixed** `.frame(height:
  noteEditorHeight)` with `autoGrow: false` (`:1148-1155`), so its frame extends *underneath* the
  raised keyboard; the last lines are rendered but unreachable. The second complaint is the same
  squeeze from the other side: the formatting bar is `ToolbarItemGroup(placement: .keyboard)`
  (`MarkdownEditor.swift:58-63`, added deliberately for monday#12297336134 sub-5), so it is
  *supposed* to appear — it just consumes more of the already-uninset height.
  *Fixed looks like:* the editor shrinks to the space above the keyboard+toolbar and scrolls, so
  the caret and the final line are always reachable.

- **D — Confirmed: stale data, not a live bug.** `f8df609` (2026-07-29) fixed the write path so a
  fully-locked enrollment can no longer persist `startDate > endDate` — it now derives **both**
  dates from the resulting schedule set. But `git show --stat f8df609` confirms it touched
  **only `server/src/services/enrollment-edit.ts`** (17 insertions, 3 deletions) — **it repairs
  nothing already written.** Scott's "AUG 3 – JUL 10" enrollment was corrupted before that commit
  and will display wrong forever until the row is repaired. `ProgramHomePage.swift:1612` is
  rendering the bad values faithfully.
  *Fixed looks like:* a one-off repair pass over `Enrollment` rows where `startDate > endDate`,
  re-deriving both from each enrollment's actual `LessonSchedule` dates (the same rule `f8df609`
  now applies on write).

- **E — NOT diagnosed; two competing readings, runtime check required.** The payload is fine:
  `/api/lessons/:id/preview-data` (`programs.ts:1913+`) **does** include
  `theme { id, slug, name, definition }` on `readBlocks`, and the iPhone authors theme at the
  **block** level (`BlockStyleEditor.swift:57,159`), which is exactly what
  `read-step.vue:234` reads (`rb.theme?.slug ?? 'none'`). So the obvious
  activity-vs-block mismatch is **ruled out**.
  1. *Content-missing (better fits the screenshot):* `read-step.vue:226-229` skips any block whose
     content is empty — `if (content.trim().length === 0) continue` — explicitly to avoid "parking
     the player on a blank slide". If both blocks resolve empty (e.g. the live scripture fetch at
     `:196-203` returns nothing), `blocks` is empty and the player renders exactly the empty body
     in shot-0. The reporter's "doesn't display the theme" would then be a *symptom* of there
     being no content at all.
  2. *Theme-only:* content renders but `themeSlug` falls back to `'none'`.
  The screenshot shows **no text whatsoever**, which favours (1) — but the reporter described a
  theme problem, so this must be confirmed before scoping a fix.

## Resolution log

### 2026-08-01 — sub-issue B only

**Resolution as specified:** *"Sub-issue B only: inset the exegesis note editor for the keyboard —
derive `noteEditorHeight` from the space above the raised keyboard plus the markdown toolbar
rather than from `Screen.bounds.height`, so the caret and final line stay reachable while the
editor scrolls internally."*

**Scope: no expansion.** One file —
`iphone/MakeReady/Pages/Manage/Program/EditExegesisActivityPage.swift` — squarely inside B's
In-scope entry. `MarkdownEditor.swift` was **not** touched, so the shared-component blast radius
flagged in Affected areas (it is also used by `EditReadActivityPage`) never materialised.
`KeyboardState.shared` is **read**, not modified — the same read-only pattern already used by
`ProgramHomePage.swift:1548`, `CreateProgramPage.swift:340`, and `GlobalSearchPage.swift:34`.

**Change (1 hunk, +29/−2):**
- New `keyboardInset` = `KeyboardState.shared.height`. `UIResponder.keyboardFrameEndUserInfoKey`
  reports the whole keyboard frame, and a SwiftUI `ToolbarItemGroup(placement: .keyboard)` — how
  `MarkdownEditor` mounts its formatting bar (`MarkdownEditor.swift:58-63`) — rides inside that
  frame as an input accessory. So one number covers "keyboard **and** toolbar", which is what the
  spec asked to subtract.
- `editorContentHeight` now reserves `keyboardInset` when the keyboard is up, falling back to
  `bottomSafeAreaInset` when it is down. The two are deliberately **not** summed: the keyboard
  frame already spans the home-indicator area, so subtracting both would over-shrink the field.
- `noteEditorHeight`'s floor drops 220 → 120 while the keyboard is raised. The 220 floor was
  itself part of the bug: with a tall keyboard it would have pushed the field straight back under
  it. A short scrollable field beats an unreachable caret.
- Keyboard-down geometry is **unchanged** — `keyboardInset` is 0 and every expression collapses to
  its previous value, so the non-editing layout is untouched.
- No new animation code: `KeyboardState` already wraps its updates in `withAnimation`, so the
  resize rides that existing animation.

**Layout assumption (evidence-backed, not runtime-verified):** the sheet is *not* pushed up by
SwiftUI's automatic keyboard avoidance — the overlay container applies
`.ignoresSafeArea(edges: .bottom)` (`OverlayManager.swift:348,543`), not `.keyboard`, and shot-3
shows the sheet's grabber still on screen with the keyboard overlapping its lower portion. Had the
sheet been pushed, its top would have been clipped off-screen instead. If a device check shows the
sheet *is* being pushed, this arithmetic double-counts and must be revisited.
