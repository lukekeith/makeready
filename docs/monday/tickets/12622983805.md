# I can still delete someone else's study

## Problem
A group leader can delete another leader's study program. Two cooperating defects:
1. **iPhone UI**: the Studies tab (`MainPrograms` — "Programs | Enrolled" header, the screenshotted page) renders the delete swipe button on **every** program card with no ownership gate, and its "Delete Program?" alert fires for programs the user didn't create.
2. **Server**: `DELETE /api/programs/:id` authorizes via `mutationFilter` (creator OR **any role-holder in the program's org** — the org-content rule introduced for edits in 8efbb7c/3afaa00), so the delete actually succeeds for non-creators.

Owner's rule for the fix (stated at deep-dive time): **group leaders may only delete their own study programs** — delete is creator-only (super-admin bypass retained); org-wide *editing* stays as designed. "Fixed" looks like: non-creators see no delete affordance on the Studies tab, and a direct DELETE call on someone else's program returns 404.

## Affected areas

### In scope
- **Platform:** multiple (server + iphone)
- **Server:** `DELETE /api/programs/:id` — `server/src/routes/programs.ts:1402-1434` (soft-delete `isActive: false`), currently scoped by `mutationFilter` (`programs.ts:63-71`). Fix narrows THIS route to creator-only + super-admin bypass; `mutationFilter` itself stays as-is for the other mutation routes.
- **iPhone:** `iphone/MakeReady/Pages/Main/StudyProgramHome.swift` — `MainPrograms.programsList` (`:527-555`): unconditional trash `SlideButton` + `isSwipeEnabled: !isDeleting`; gate both with `program.isEditable(by: authManager.currentUser?.id)` exactly like MainLibrary's browse list (`MainLibrary.swift:695-704`). The alert/deleteProgram plumbing (`:140-152`, `:755+`) stays.

### Explicitly out of scope
- `MainLibrary.swift` (Library tab, "Programs | Media") — its browse list already gates delete on `isOwn` (`:695-704`); untouched.
- Web LeaderApp `client/resources/js/islands/leader-app/views/library-view.vue` — already creator-gates delete (`isOwn`, `:387-388`, `:551-552`); no change.
- All OTHER program mutation routes (PATCH program, activities, read blocks, publish, etc.) — org-wide manage via `mutationFilter`/`canManageOrgContent` is the intended design (8efbb7c, 3afaa00); do NOT narrow them.
- `DELETE /api/programs/:id/permanent` — API-key-only maintenance route; untouched.
- `services/permission.ts` (`canManageOrgContent`, `getManageableOrgIds`) — shared authorization helpers used across many routes; do not modify.
- iPhone `ProgramHomePage` (Manage) / `ProgramHomeModalContent` — no program-delete affordance there; untouched.

### Cross-app impact
Server tightening affects every client's delete call: web LeaderApp and MainLibrary already hide delete for non-creators, so only `MainPrograms` behavior visibly changes (button disappears; a stale client would get 404). Org owners/admins also lose delete on others' programs per the owner's rule; super admins retain it.

## Root cause
Commits 8efbb7c/3afaa00 ("Authorize org content by org role") replaced creator-only checks with org-scoped `mutationFilter` across program mutations INCLUDING the delete route (`programs.ts:1408`), while the iPhone Studies tab (`StudyProgramHome.swift:531-537`) never had an ownership gate on its delete swipe (its sibling MainLibrary list did). Together: any leader with a role in the org can both see and successfully execute deletion of any org program.

## Verification
1. **Code-level proof:** `programs.ts:1408` (`mutationFilter` in the DELETE lookup) + `programs.ts:69` (org role-holders pass the filter); `StudyProgramHome.swift:531-537` (ungated trash) vs `MainLibrary.swift:695-704` (gated sibling).
2. **Server test harness:** the authenticated API tests added in 8efbb7c (`server/src/routes/__tests__/`) can assert a second org leader's DELETE returns 404 while the creator's succeeds (needs dockerized test DB on :5433).
3. **Manual repro:** two leader accounts in one org; leader B opens Studies tab → swipe leader A's program → trash shows → Delete succeeds (bug). Fixed = no trash for B (swipe inert), and `curl -X DELETE /api/programs/{id}` as B → 404; creator still deletes fine.
