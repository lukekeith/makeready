# I’m confused

> **Board note:** this ticket lives on board **18424266955 ("V1.1.3 (344)")**, group *UX issues* — not
> the pipeline's default board `18413909869`. That board has its own column ids (see § Classification).

> **Sibling ticket:** [`12668543338`](12668543338.md) **sub-issue D** is the *same screen and the same
> mode* — "after I select a verse and then Highlight it, I'm stuck in the editor". That one was about
> **getting out** of highlight mode and is fixed (`0cd956c`, pending verification). This ticket is

## Problem

iPhone, leader authoring. In the **Edit Activity** modal for a **Read** activity, tapping the
highlighter glyph on a Bible-verse block (the reporter reads it as a "pencil icon") puts the block
into highlight mode. What the user then sees is **two lollipop text-selection grab handles floating
in the verse text with no highlighted span between them, and no instruction anywhere about what
highlight mode expects**. The handles are UIKit's native selection handles, tinted lime by this
view; the selection *fill* they are supposed to bracket is not drawn, so the two knobs read as
"disconnected" — the reporter's exact word — and mean nothing.

Two defects sit on top of each other:

1. **Rendering** — the in-progress selection has no attribute-backed fill in this component, so the
   only feedback is UIKit's transient tint, which every SwiftUI re-render wipes out from under the
   handles (mechanism below). The Exegesis editor hit the same wall and solved it by painting the
   preview itself; the Read editor never got that treatment.
2. **Affordance** — entering highlight mode changes exactly two pixels' worth of state (a 24×24 glyph
   turns purple, the card border turns purple). Nothing says "tap a verse to select it, tap again to
   choose a style", and the commit gesture is *tap inside the live selection*, which is not a gesture
   any user guesses.

**Fixed observably:** entering highlight mode tells the user what to do; selecting a verse paints a
visible span (not two orphaned knobs); and the step that opens the style picker is discoverable
without instruction from the developer.

## Root cause

**The in-progress selection lives only inside UIKit, and SwiftUI stomps the text under it on every
re-render — leaving the handles behind with nothing to bracket.**

1. Selection is applied imperatively to the `UITextView`:
   `applyVerseTap` sets `textView.isSelectable = true`, calls `becomeFirstResponder()` and assigns
   `textView.selectedRange` (`SelectableLockedBlockView.swift:259-263`). Nothing about that range is
   written back into SwiftUI state — `pendingRange` is only set at *commit* time (`:244-246`,
   `:207-211`), not while the selection is live.
2. The only feedback for a live selection is UIKit's own tint — `view.tintColor` at `:56`
   (`#F4FF76` @ 0.5). `makeAttributedString()` (`:120-155`) paints **saved** `ReadBlockSelection`
   records (purple, `:150`) and the range currently being styled (`:144-145`), but has **no case for
   the in-progress selection**.
3. `updateUIView` reassigns `uiView.attributedText = makeAttributedString()` on **every** SwiftUI
   update (`:80`) and re-lays out the verse badges (`:83-87` → `SelectionTextView.layoutSubviews`
   `:327-336`). Replacing the text storage drops the transient selection rendering; the first
   responder's selection handles persist. The re-sync guard at `:90-95` fires **only when
   `isSelectionEnabled` is false**, i.e. only on the way *out* of highlight mode — so during
   highlight mode the desync is never repaired. Result: two grab handles, no fill. That is precisely
   the screenshot.
4. **The Exegesis editor proves the diagnosis by contrast.** `ExegesisVerseView` does not trust the
   system tint: it paints the live native selection itself as a `.backgroundColor` attribute
   (`ExegesisVerseView.swift:665-666`, colour `:117` — the *same* `#F4FF76`, at 0.55) and manages
   `nativeSelectionPreviewRange` explicitly (`:129`, `:467`, `:508`, `:678-691`). The Read block was
   never given that treatment.

**Secondary (and what the reporter actually wrote): the mode has no affordance.** Entering highlight
mode changes only the glyph tint (`EditReadActivityPage.swift:741`) and the card border
(`:719-721`). The intended interaction — tap a verse to select, tap another to extend, **tap inside
the selection to commit and open the style picker** (`SelectableLockedBlockView.swift:232-249` →
`EditReadActivityPage.swift:1221-1256`) — is documented only in code comments. "Tap the thing you
already selected to confirm it" is not a gesture users guess, and the entry point is an unlabeled SF
`highlighter` glyph (`:739`) that the reporter reasonably read as a generic "pencil / edit" button.

**Verified in code (2026-08-03).** The rendering mechanism (points 1–3) is proven at the cited lines;
the *exact* handle positions in the screenshot (start of verse 1, mid-verse 3 rather than a verse
boundary) additionally suggest the user reached a character-level native selection after `isSelectable`
was latched to `true` at `:260` and never reset — worth confirming on a device, but it does not change
the fix.

## Verification

**Code-level proof (strongest) — no device needed for the defect itself:**
- `SelectableLockedBlockView.swift:56` sets the exact lime tint that the screenshot's knobs render in,
  identifying them as this view's native selection handles.
- `SelectableLockedBlockView.swift:120-155` contains no branch that paints the in-progress selection —
  only saved `selections` and the `editingRange`.
- `SelectableLockedBlockView.swift:80` reassigns `attributedText` on every update; the compensating
  re-sync at `:90-95` is gated on `!isSelectionEnabled`, so it never runs during highlight mode.
- Contrast: `ExegesisVerseView.swift:665-666` explicitly paints the equivalent preview, i.e. the
  codebase already concluded the system tint alone is insufficient.

**Manual repro (iPhone, leader account):**
1. Program → lesson → a **Read** activity that contains a Bible-verse block (e.g. John 1:1-3).
2. Tap the highlighter glyph at the block's top-right. Observe: purple border + purple glyph, and
   **no instruction of any kind**.
3. Tap a verse. Observe the two grab handles appear; the highlighted span is not reliably painted,
   and disappears on the next re-render (e.g. type in the title field, collapse/expand another block).
4. Note that nothing indicates the next step is to tap *inside* the selection to open the style picker.

**Capture:** `component.SelectableLockedBlockView` already exists in the capture ViewRegistry
(`iphone/MakeReadyCaptureTests/ViewRegistry.swift:2069-2084`), but its fixture has no
"selection in progress" state — a new fixture variant would be needed to pin this visually, since
`isSelectionEnabled` alone does not produce a selection.

## Resolution log

### 2026-08-03 — full fix (`9ff035f`)

**Resolution as specified by Luke:** *"Paint the in-progress selection in
SelectableLockedBlockView.makeAttributedString() as a .backgroundColor attribute the way
ExegesisVerseView does, mirror the live selectedRange into SwiftUI state so updateUIView re-applies
it instead of wiping it, and add a visible hint in Read highlight mode telling the user to tap
verses to select and tap again to style."*

**One design fork put to Luke before implementing** (it changes visible behaviour and the resolution
text didn't decide it): once the block paints its own span, should UIKit's native grab handles still
appear? Options were (a) drop them by no longer latching `isSelectable`/`becomeFirstResponder`, or
(b) keep them and sync handle-drags back into SwiftUI state. **Luke chose (a).** So `selectedRange`
is not re-applied to the text view — the mirrored SwiftUI state *is* the selection, and
`updateUIView` re-applies it as paint. That is the one deliberate departure from the literal wording
of the resolution.

**Files changed** (3 — all on the dossier's approved list):
- `iphone/MakeReady/Components/Content/SelectableLockedBlockView.swift` — new
  `@Binding var liveSelection: NSRange?`; `makeAttributedString()` paints it last as a lime
  `.backgroundColor` + black `.foregroundColor` (`liveSelectionColor`, the same `#F4FF76` @0.55
  `ExegesisVerseView` uses); `applyVerseTap` no longer takes a text view, reads and writes the
  binding instead of `textView.selectedRange`, and no longer flips `isSelectable` /
  `becomeFirstResponder`. Removed: the `tintColor`, the leaving-highlight-mode selection reset in
  `updateUIView`, the dead `suppressSelectionCallbacks` flag and the no-op
  `textViewDidChangeSelection` — all four existed only to serve the system selection that is gone.
- `iphone/MakeReady/Pages/Manage/Program/EditReadActivityPage.swift` — `liveSelectionRange` /
  `liveSelectionBlockId` state + the per-block `Binding`; both existing highlight-mode exits (the
  toggle and `exitHighlightModeIfActive()`) clear them; hint row
  **"Tap verses to select, then tap again to style"** shown while highlighting.
- `iphone/MakeReadyCaptureTests/ViewRegistry.swift` — `liveSelection: .constant(nil)` for the new
  binding. Pre-authorized by this dossier's shared-component callout; `CaptureFixture.swift` needed
  no change since no fixture field was added.

**Scope:** nothing outside the approved list. The Exegesis editor, the other activity editors,
`BibleVerseTextLayout.swift` and the web twin were not touched. The working tree also carries
**unrelated pre-existing edits** (`PageTitle.swift`, `Route.swift`, `EditExegesisActivityPage.swift`,
`project.pbxproj`, untracked `ExegesisNoteEditorPage.swift`) that predate this session — deliberately
left out of the commit. `Info.plist`'s CFBundleVersion bump is the auto-increment build phase's
artifact and was excluded too.

**Review catch:** the hint initially carried `.transition(.opacity)`. `/transition-review` failed it
on **C4** — it sits inside a `SwipeableCard`, where transition modifiers make children animate
independently of the card during a swipe (`SWIFTUI_ANIMATION_PATTERNS.md` § Swipeable Cards). Removed;
the `withAnimation(Motion.micro)` around `highlightingBlockId` already fades the insert. Re-reviewed:
**PASS** (A1–A4, B1, B4, C2, E1–E3 green; the rest N/A).

**Race closed during implementation:** the first cut mirrored the selection via
`DispatchQueue.main.async`, which opened a window where a fast second tap read a stale value — the
original read `textView.selectedRange` synchronously and had no such window. The `liveSelection`
writes are synchronous; the pre-existing async `pendingRange` write is unchanged.
