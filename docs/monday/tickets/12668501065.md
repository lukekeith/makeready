## Preview architecture (governs C and E) — owner model, 2026-07-30

**The model:** there are two parallel preview systems, and they must share the same UI.

1. **Study program preview** — preview a study program that has *not* been enrolled, simulating
   the member experience. For curriculum a leader is still building.
2. **Enrollment preview** — preview an *enrollment*, i.e. what a specific group actually has.

### The two hierarchies are isomorphic (owner, 2026-07-30)

```
study program   =  program      →  lessons          →  activities
                   StudyProgram →  Lesson           →  LessonActivity

enrolled study  =  enrolled     →  lessons          →  activities
                   Enrollment   →  LessonSchedule   →  ScheduledLessonActivity
```

Three levels on each side, one-to-one. **The only difference is the schedule:** an Enrollment
carries real dates (`Enrollment.startDate` / `enabledDays` / `timezone`, and `scheduledDate` on
each `LessonSchedule`); a StudyProgram carries none of these — `StudyProgram` has only `days`
(an Int count), and the meeting pattern lives entirely on `Enrollment`.

**So the study-program preview must simulate a schedule starting from today**, letting both
sides feed the same view with the same shape. Note the cadence differs by necessity: real
enrollment scheduling advances the cursor to the next *enabled weekday*
(`enrollments.ts:4757-4767`, `enabledDayNumbers.includes(cursor.getDay())`), but a program has
no `enabledDays` to draw on — so the simulation should use **consecutive days from today**, and
its dates should read as illustrative rather than committed.

## Root cause

- **A — NOT a defect; agreed design decided 2026-07-30.** Non-editable highlights were
  **intentional** (owner's call). `EditExegesisActivityPage.swift` presents
  `HighlightActionMenuContent` whose action group (~1100-1135) is PREV/NEXT + note + Delete;
  `ExegesisVerseView` (:463-479) exposes `onRangeSelected` / `onHighlightTapped` only.
  **Agreed approach:** add an **edit icon button to the note row** in the highlight pane; it
  dismisses the pane and puts that highlight into edit mode (native UITextView selection,
  seeded with the highlight's current range) so the handles can be dragged.
  *Fixed looks like:* tap highlight → pane → edit icon → pane dismisses, handles appear on the
  existing span → adjust → confirm → span updated in place, note preserved.

  **Four implementation constraints (verified in code — do not skip):**
  1. **Must NOT save via `applyStyle(.highlight,…)`.** That path calls
     `actions.createHighlight` (:806-824), which is the *merge* path — the server unions any
     touched highlight (`e989fb4`) and the client drops overlapping locals (:817-819). A
     shrunken range still overlaps the original, so it unions straight back: **edit-to-grow
     works, edit-to-shrink silently no-ops.** Add a `PATCH` on the highlight id that sets
     start/end instead. Additive — merge-on-create is untouched. **This also resolves B**,
