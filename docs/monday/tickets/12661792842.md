# logic error (enrollment date edit saves startDate > endDate)

## Problem
Editing an enrollment's dates on the iPhone app (Program Home → Enrollments tab → tap enrollment → gear/action menu → Edit enrollment → schedule drilldown) can persist an enrollment whose **startDate is after its endDate**. The enrollment card then displays an impossible range like "AUG 3 - JUL 10". This is NOT an app-state issue — production data confirms the server stores the inverted range. Mechanism: the server's reschedule never moves "locked" lessons (SMS already sent, or scheduled date in the past), and recomputes `endDate` from the actual final schedule set — but writes the requested `startDate` **unconditionally**. When every lesson is already locked (the study has fully elapsed), a date edit moves zero lessons yet still overwrites startDate, producing start > end. "Fixed" observably looks like: after any enrollment date edit, the stored/displayed range is always start ≤ end and matches the real lesson schedule; an edit that cannot move any lessons either warns or is rejected instead of silently corrupting the record.

## Root cause
`server/src/services/enrollment-edit.ts:334-341` — `applyEnrollmentEdit` writes the requested `startDate` unconditionally while recomputing `endDate` from the final schedule set, and locked lessons (smsSentAt set, or scheduledDate ≤ now — `isLocked`, line 66) never move. For a fully-elapsed enrollment every lesson is locked, so `computeRescheduledDates` returns an empty change-set: endDate stays at the historical last-lesson date while startDate jumps to the newly requested date → startDate > endDate persisted. The preview path has the matching gap: zero moved lessons ⇒ no warning shown before Save.

## Verification
1. **Code-level proof:** `enrollment-edit.ts:334-341` (unconditional startDate write) vs. `:135-159` (locked lessons excluded from rescheduling) — the asymmetry is visible in the source.
2. **Production data proof:** enrollment `26fcc227…` has startDate 2026-08-03 > endDate 2026-07-10 (queried via production API 2026-07-29).
3. **Manual repro (local):** create an enrollment whose lessons are all in the past (or set scheduledDates/smsSentAt in DB), then `PATCH /api/enrollments/:id` with a future `startDate` + `enabledDays`. Observe the row now has startDate > endDate. After the fix, the stored startDate must equal the first actual scheduled date (unchanged), and ideally the preview warns that nothing will move.
