> 🔴 **This is a regression we introduced.** Build 374 is HEAD (`3d7f8c0`); the fix for
> [`12668695071`](12668695071.md) landed at `9ff035f` = build **372**, so it is in the build Scott is

## Problem

iPhone, leader authoring, **Edit Read Activity**. After entering highlight mode on a Bible-verse
block, applying a highlight, and exiting the mode, the verse block's card **loses its rounded
corners** — the 12pt radius is gone and the card renders as a hard-edged rectangle. The card's
`Color.cardBackground` fill reaches the exact corner pixel, so the corner is genuinely square, not
merely subtle. The sibling card directly above it (the "Write content…" markdown editor) keeps its
rounded corners in the same screenshot, which rules out a global/theme cause.

**Fixed observably:** after highlighting a passage and leaving highlight mode, the verse card still
has 12pt rounded corners and its hairline border, identical to how it looked before entering the mode.

## Root cause

**Not fully diagnosed — but the trigger is pinned and the responsible commit is near-certain.**

What is established:
1. The card's rounding is unconditional in code (`:745-746`), so no state should ever square it.
2. It is nonetheless square at runtime, proven by pixel probe, in the post-exit state.
3. It was round on build 344 and is square on build 374.
4. `9ff035f` (build 372, in 374) introduced the **first and only** thing that changes this card's
   **height** as a function of `isHighlighting`: the hint at `:705-716`. Before it, entering/leaving
   highlight mode changed only colours and stroke width — never geometry.
5. The reporter's repro — *enter highlight mode → add a highlight → **exit*** — is exactly the
   sequence that grows the card and then shrinks it again, animated by `withAnimation(Motion.micro)`.

**Leading hypothesis:** the card is a SwiftUI subtree hosting a `UIViewRepresentable`
(`SelectableLockedBlockView`) inside a `SwipeableCard`, so its `.clipShape` is realised as a layer
mask on a UIKit-hosted layer. When the card's height shrinks on exit, the mask does not shrink with
it; a mask larger than its layer leaves the layer's own corners outside the mask's arcs, and the
result renders square. This explains why the neighbouring `MarkdownEditor` card — same idiom, but
**no height change and no SwipeableCard wrapper** — is unaffected in the same screenshot.

**Secondary hypothesis:** the animated frame change leaves the clip shape's bounds stale for the
duration/after the animation, independent of UIKit hosting.

Distinguishing the two needs a device repro; both point at the same fix, which is to stop depending
on a mask for the rounding and/or stop changing the card's height.

## Verification

**Manual repro (primary — this one genuinely needs the device):**
1. iPhone build ≥372, leader account → a Read activity containing a Bible-verse block.
2. Tap the highlighter glyph → note the hint appears and **the card grows**.
3. Tap verses to select, tap again, choose **Highlight** → the purple span saves.
4. Exit highlight mode (the glyph, Cancel/Done, or background tap) → **the card's corners are square.**
5. Control: repeat steps 2 and 4 *without* applying a highlight, to establish whether the highlight
   itself matters or whether the enter→exit height change alone is sufficient. This single check
   separates the two hypotheses above and should be the first thing /monday-resolve does.

**Bisect proof available without a device:** temporarily render the hint unconditionally (so the card
height never changes) and see whether the artifact disappears. That isolates the hint as the cause
without guessing at SwiftUI internals.

**Capture:** `component.SelectableLockedBlockView` exists in the ViewRegistry but captures the block
component, not the enclosing card, and has no enter→exit sequence — it cannot reproduce this. An
`EditReadActivityPage`-level fixture with a post-exit state would be needed.

**Code-level:** none available — the code says the corners are round; the defect is in how SwiftUI
realises it. Do not expect a file:line proof for this one.

## Resolution log

### 2026-08-03 — fix (`82ddba8`)

**Resolution as specified by Luke:** *"In EditReadActivityPage.lockedBlockView, paint the card's
rounding instead of masking it — replace .background(Color.cardBackground).clipShape(RoundedRectangle
(cornerRadius: 12)) with .background(RoundedRectangle(cornerRadius: 12).fill(Color.cardBackground)) —
and stop the card's height changing on highlight-mode toggle by moving the hint outside the card,
verifying with the enter/exit control repro."*

**Files changed** (1 — the only file on the In-scope list):
- `iphone/MakeReady/Pages/Manage/Program/EditReadActivityPage.swift`
  - card chrome: `.background(Color.cardBackground)` + `.clipShape(RoundedRectangle(cornerRadius: 12))`
    → `.background(RoundedRectangle(cornerRadius: 12).fill(Color.cardBackground))`. Dropping the clip
    is safe because content is inset `.padding(16)`, well clear of the 12pt corner arc.
  - the hint moved out of the card's VStack into a new wrapping
    `VStack(alignment: .leading, spacing: 8)` that holds `[hint?, card]`, with
    `.padding(.horizontal, 16)` moved onto the wrapper so outer geometry is unchanged. The
    `SwipeableCard` is now bound to a local `let card` to keep the diff free of a ~115-line
    re-indent.

**Placement decision — hint ABOVE the card, not below.** A verse block can be taller than the
viewport (Scott's own Hosea 13:2-7 fills the screen), so a hint underneath it would be scrolled out
of sight and would not solve the discoverability problem it was added for in
[`12668695071`](12668695071.md). Above it is also where the eye already is, next to the glyph that
was just tapped. Cost: the card shifts down ~28pt when the mode opens — an outer-layout move, which
is exactly the kind that does *not* touch the card's own clip.

**Both halves of the resolution were implemented even though either might suffice on its own** —
this card has now regressed twice, and the mechanism was never proven statically (see § Root cause).
Painting the rounding removes the failure mode; freezing the card's height removes the trigger.

**Scope:** `SwipeableCard.swift` was **not** touched — the dossier's 14-consumer tripwire never
fired, and no sign-off was needed. Nothing outside the approved file. `Info.plist`'s CFBundleVersion
bump is the auto-increment build phase's artifact and was excluded from the commit.

**Transition self-check:** the diff adds no `withAnimation` / `.transition(` / `.animation(` /
lazy container / `asyncAfter` — the only mentions are in comments — so `/transition-review`'s trigger
set is not met. Rule **C4** (no transition modifiers on content inside a `SwipeableCard`) is strictly
improved: the hint is no longer inside the card at all. The insert still animates under the
unchanged `withAnimation(Motion.micro)` on the highlighter toggle.
