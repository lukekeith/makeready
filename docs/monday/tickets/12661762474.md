## Data & endpoint inventory (2026-07-29 deep dive)
**Real engagement signal lives in the member-progress tables, NOT the activity ledger** — `ActivityAction.COMPLETED/ENROLLED/SUBMITTED` exist in the enum but are never written; the `activities` ledger tracks authoring/admin actions, and `activity_logs` is auth/route audit noise (engagement.ts:6-10 says so explicitly).

- `MemberActivityProgress` (prisma:1269-1292) — per member × scheduled activity, `completedAt`, analytics index `(lessonScheduleId, scheduledActivityId, completedAt)`.
- `MemberVideoProgress` (prisma:1294-1319) — adds `watchedSeconds`, `watchPercentage`, completes at ≥90%. Video completions live HERE, not in MemberActivityProgress — correct counts must UNION both.
- `MemberLessonProgress` (prisma:1321-1340) — per member × lesson schedule, `completedAt`.
- Study notes count as engagement via `note_links(refType='ENROLLMENT')` (engagement.ts:75-110 unions all three sources).
- Join path to program: `progress → lessonSchedule → enrollment(studyProgramId) → group`.
- `AiLessonSummary.memberSummary` deliberately null when member wrote nothing — usable as "reflection rate".

**Existing endpoints (none are program-scoped today):**
- `GET /api/enrollments/:id/completion-stats` (enrollments.ts:1534) → `enrollment-analytics.service.ts` `getEnrollmentCompletionStats`: memberCount + per-lesson/per-activity distinct-member completion counts (UNIONs video+activity, current-version-only). Org-scoped access. The service header names its own extension point: `getEnrollmentCompletionDetail(enrollmentId)` for per-member who/when — "no new tables required".
- `GET /api/engagement/heatmap` + `/weekly` (engagement.ts:132/197) — day×hour buckets and zero-filled daily counts, timezone-aware, `days` 1-366 — **group-scoped** via `resolveLeaderGroupIds` (creatorId-only; same authorization gap as memory `group-leader-org-authorization`). Minimal change: accept `programId` and scope events by the program's enrollments.
- `GET /api/activity-logs/stats*` — audit-log aggregates; wrong signal for this tab.

**iPhone building blocks (all exist, mostly unused):** `Components/Chart/` — `LineChart` (TimeScale .hours….years, multi-line, area), `VerticalBarChart`, `HorizontalBarChart`, `DonutChart` (+legend), `HeatMapChart` (brand 4-stop ramp); `Components/Display/Kpi.swift` (.standard/.compact/.sparkline/.iconValue + trend sparkline). LineChart/DonutChart/HorizontalBarChart have ZERO production call sites. `MainHome.chartsSection` (:585-645) is the reference for the requested "like the dashboard" heatmap (7×24, chartHeight 576, x=day labels, y=12a…11p) — note MainHome maps `bucket.day → week` and `bucket.hour → day` (HeatMapChart field names are transposed; mirror this mapping). API decode models `HeatmapBucket`/`DayActivityCount` currently live at the bottom of `MemberHomePage.swift:1098-1120`. `EnrollmentCompletionStats` models already exist (EnrollmentModels.swift:539-556) with action `EnrollmentActions.getEnrollmentCompletionStats` (consumed today only by `EnrollmentSchedulePage` card fill).

## Recommended design (deep-dive deliverable, 2026-07-29)
Layout top-to-bottom on the Analytics tab (unfiltered, program-scoped):
1. **KPI row** (2×2 `Kpi` .compact): Members reached (distinct members w/ any progress) · Active enrollments (of total) · Lessons completed (total) · Completion rate (completions ÷ members×lessons). Optional sparkline trend on the first two.
2. **Recent activity** — segmented control `Week / Month / Year` over `LineChart` (TimeScale .days/.weeks/.months) fed by zero-filled daily counts (engagement `/weekly` pattern with `programId`, days=7/30/365). Covers "total activity + recent activity" asks.
3. **Activity heatmap** — `HeatMapChart` 7×24 exactly like MainHome (Scott's explicit ask), fed by `/api/engagement/heatmap?programId=…` (default 30 days rather than 7 for denser program-level data).
4. **Lesson funnel ("popular content" + drop-off)** — `VerticalBarChart`: x = Day 1…N (curriculum dayNumber), y = distinct members completed. Shows both the most-completed lessons AND where members drop off — the single most actionable program-authoring chart. Aggregate of per-enrollment completion-stats across all the program's enrollments.
5. **Content mix** — `DonutChart` of completions by activity type (VIDEO/READ/EXEGESIS/WRITE) + legend; center label = total completions. First production DonutChart use.
6. **Top members** — top 5-10 leaderboard rows (avatar + name + group + completions count; reuse member row/card components) from the service's named extension point (per-member completion detail aggregated program-wide).
7. **Top enrollments** — ranked rows (group name + `HorizontalBarChart`-style fill or percent badge): completion % per enrollment = lessonCompletions ÷ (members × lessons). Answers "which groups are thriving".
8. **Extra ideas (cheap, data already exists):** video watch time KPI (`SUM watchedSeconds` + avg watchPercentage); notes written count (already an engagement event); reflection rate (AiLessonSummary.memberSummary non-null ÷ completions); enrollment growth line (enrollments created per month); pace donut (ahead/on-pace/behind from daysAhead — needs per-member schedule walk, defer).
Server shape: ONE `GET /api/programs/:id/analytics` returning `{kpis, funnel, contentMix, topMembers, topEnrollments}` (single round trip, org-scoped like completion-stats, raw SQL over the indexed progress tables) + `programId` on the two engagement endpoints for the time-series/heatmap (they already own timezone/zero-fill logic). Cache-first on iPhone per house pattern (AppState field + disk persistence optional).
Phasing if desired: Phase 1 = KPIs + recent activity + heatmap (pure reuse of engagement patterns); Phase 2 = funnel + content mix + leaderboards (new aggregate endpoint).
