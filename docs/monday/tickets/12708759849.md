## Problem

iPhone, leader authoring, **Exegesis activity editor**. Three distinct defects in the same
highlighting interaction, all reported within six minutes on build 374:

| # | Report | Severity | Status |
|---|---|---|---|
| **A** | Highlighting over two existing highlights **erased the notes** attached to them | data loss | **client-side, not isolated** |
| **B** | The drag lets you select **down to the letter** — "this should never happen" | UX correctness | **proven in code** |
| **C** | The highlight **locks itself in after an arbitrary time**, mid-gesture, and is then impossible to edit | dominant complaint | **proven in code** |

Luke's framing of C, which is the spec for the fix: *"the iPhone app suddenly releases the tap and
hold before the user actually releases their finger from the iPhone. This is a very very annoying UX.
The highlight should continue to be editable after the tap and hold until the user releases the tap
and hold. It should never release before that."*

**Fixed observably:** (A) merging highlights keeps every note; (B) a drag snaps to whole words (or
verses) and cannot land mid-word; (C) the selection stays live and adjustable for as long as the
finger is down, and commits **only** on lift.

## Root cause

### C — the commit is on a timer, and its "is the finger down?" signal is unreliable. **Proven.**

Every selection change schedules a commit **0.8 s** later
(`ExegesisVerseView.swift:758`, `nativeSelectionChangeSettleDelay` `:148`). The scheduled work item's
only protection against firing mid-gesture is:

```swift
if self.isNativeSelectionTouchActive {           // :772
    self.scheduleNativeSelectionCommit(reason: "\(reason) touch still active", delay: 0.25)
    return
}
```

`isNativeSelectionTouchActive` is set in the text view's own `touchesBegan` (`:216`) and cleared in
`touchesEnded` (`:226`) **and `touchesCancelled` (`:238`)** — and `touchesCancelled` additionally
*schedules a commit* at `nativeSelectionTouchEndCommitDelay = 0.5 s` (`:240`, `:146`).

UIKit delivers `touchesCancelled` to a view when a gesture recognizer takes over the touch — which is
exactly what `UITextView`'s own text-selection interaction does when a long-press turns into a drag.
So mid-gesture, with the finger still on the glass, the view concludes the touch ended, and half a
second later the commit body runs:

```swift
self.clearNativeSelectionPreview(...)            // :797  — the wash disappears
self.selectedRange = NSRange(location: 0, length: 0)  // :798 — the selection is dropped
if self.isFirstResponder { _ = self.resignFirstResponder() }  // :799-801 — handles vanish
self.onRangeSelected?(selectedRange)             // :802  — the highlight is created
```

That *is* the reported symptom, exactly: the app "releases the tap and hold before the user actually
releases their finger", the highlight "locks in after an arbitrary time" (0.5 s or 0.8 s depending on
which path won), and it is then "impossible to edit" because the selection and first-responder state
are gone. **verified in code (2026-08-03)**

### B — nothing constrains the range to word or verse boundaries. **Proven.**

`onRangeSelected?(selectedRange)` (`:802`) forwards the raw `UITextView.selectedRange`. UIKit's drag
granularity is per-character, so a drag can and does land mid-word; the committed highlight then
carries that range verbatim into `createHighlight` (`EditExegesisActivityPage.swift:935-941`). There
is no snapping step anywhere between. The screenshots show the consequence — spans starting at
"because" and ending at "the"/"and", mid-clause. **verified in code (2026-08-03)**

### A — the server is exonerated; the loss is client-side. **ISOLATED + FIXED 2026-08-04 (`6e349b5`) — hypothesis 1 below was correct.** See § Resolution log.

The merge endpoint explicitly preserves notes (`server/src/routes/programs.ts:3033-3045`):

```ts
// Overlapping highlights merge: the new range absorbs every highlight it
// touches — union span, notes concatenated in document order.
const noteMarkdown = [...absorbed.map((h) => h.noteMarkdown), sanitizeMarkdownInput(body.noteMarkdown)]
  .filter((n) => n && n.trim())
  .join('\n\n')
```

…and the created row (carrying that concatenation) is what the endpoint returns (`:3060-3073`).
`syncExegesisSelectionsForBlock` (`:2894-2907`) only rewrites the block's `selections` JSON —
start/end/style — and never touches `noteMarkdown`. The client then stores the returned note
(`EditExegesisActivityPage.swift:950`). On this reading the note should survive.

So one of these is true, and **the deep dive cannot tell which without a repro**:
1. **The note survives in the database but is unreachable in the UI.** The client's note dictionary is
   keyed by *range* — `highlightNoteKey` is `"\(location):\(length)"` (`:649-651`). A merge changes
   the span, so every pre-merge key is stale by construction. Indistinguishable from deletion to
   Scott. This is the same failure *class* as `12668543338` sub-issue A (a note that existed but the
   UI insisted did not), and the surrounding code was rewritten in `3d7f8c0` — which is in build 374.
2. **Something overwrites the merged note with an empty string** after creation — e.g. a note draft
   flushed for the new highlight. `ExegesisNoteEditorPage` holds `savedNoteMarkdownByHighlight` and
   `noteDrafts` as bindings and is new in this build.
3. Less likely: the loss is real and server-side via a path not read here.

The two live possibilities need different fixes (re-key by highlight id vs. stop an empty-draft
flush), which is why this must be reproduced before it is "fixed".

**Answered 2026-08-04: hypothesis 1.** The API-level repro returned the merged row carrying all four
notes concatenated, so the text was in the database the whole time and the range-derived key was
stale. Hypothesis 2 (an empty draft overwriting the note) and 3 (a server path not read here) are
both ruled out by that same observation. Insisting on the repro was right — the fix for 1 and the fix
for 2 have nothing in common.

## Resolution log

### 2026-08-03 — sub-issues C and B (`c8a0311`). **A deliberately untouched.**

**Resolution as specified by Luke:** *"Fix sub-issue C first in ExegesisVerseView: replace the
asyncAfter commit timers (nativeSelectionChangeSettleDelay/nativeSelectionTouchEndCommitDelay) with a
commit driven by the real end of the selection gesture so the selection stays live and adjustable
until the finger lifts, and snap the committed range outward to word boundaries for sub-issue B —
leaving sub-issue A until the database repro shows whether the notes are actually gone."*

**Files changed** (1 — the only file needed; `EditExegesisActivityPage.swift` was **not** required):
- `iphone/MakeReady/Components/Content/ExegesisVerseView.swift`
  - **New `TouchObserverGestureRecognizer`** (end of file) — never recognizes, so it never competes
    with the text-selection interaction, and stays in `.possible` forever so UIKit keeps delivering
    it the whole touch sequence. Failing would stop delivery; recognizing would steal the gesture.
    This is what makes "the user actually let go" knowable.
  - `activeTouchCount` + `handleActiveTouchCountChanged(_:)` — single source of truth for whether a
    finger is down. Count > 0 cancels any queued commit and keeps the selection live; count → 0
    (having been > 0) commits.
  - `scheduleNativeSelectionCommit(reason:delay:)` → **`commitNativeSelectionAfterLift(reason:)`**.
    No timers: one `DispatchQueue.main.async` hop so UIKit can settle `selectedRange` after the
    lift, re-guarded by `activeTouchCount == 0` so a finger back down abandons it.
  - `textViewDidChangeSelection` no longer schedules anything — a selection change means the user is
    still choosing.
  - `touchesBegan/Ended/Cancelled` keep their scroll-freeze bookkeeping but no longer decide the
    gesture is over. **This is the actual bug**: `touchesCancelled` fires with the finger still down.
  - **`snappedToWordBoundaries(_:in:)`** — widens the committed range outward to whole words,
    treating `'`, `’` and `-` as intra-word so "Lord's" and "God-fearing" stay whole. Grow-only.
  - Removed `nativeSelectionTouchEndCommitDelay` (0.5) and `nativeSelectionChangeSettleDelay` (0.8),
    and `isNativeSelectionTouchActive` — `activeTouchCount` replaced its only read, leaving it
    write-only.

**Deliberate limit on B, disclosed:** the resolution said to snap *the committed range*, so that is
what was done. The **live drag preview still tracks the finger per character**; only the saved
highlight is word-aligned. Snapping the preview too would make the drag itself feel word-wise, but it
would also desync the lime wash from UIKit's own selection handles, which sit at unsnapped positions
— a visual inconsistency worth deciding on deliberately rather than inventing here.

**Shared-component result — blast radius is nil.** `ExegesisVerseView` has three in-app consumers,
but only `EditExegesisActivityPage` passes `usesNativeTextSelection: true` (`:457`);
`ExegesisHighlightModal` and `ExegesisNoteEditorPage` leave it `false`, and every line changed here
is gated on `usesNativeSelection`. The dossier's shared-component callout is therefore satisfied
without touching either of them.

**Scope:** nothing outside the approved file. Sub-issue A untouched, per the resolution.
`Info.plist`'s CFBundleVersion bump is the auto-increment build phase's artifact and was excluded.

### 2026-08-04 — sub-issue A RESOLVED (`6e349b5`). Hypothesis 1 was correct.

Done as Phase 1 of the `highlighting` feature spec (`docs/features/highlighting/`), which made this
fix a hard prerequisite: that spec migrates every Read highlight into the same table this merge path
writes, and it forbade moving data into a write path with an open loss report.

**The decisive check, run exactly as § Verification specified.** An API-level repro on the local
stack — stronger than the simulator, because it removes the client from the picture entirely. On a
block already carrying four highlights, two of them noted, a new highlight spanning both was created.
The merged row came back holding **all four notes concatenated in document order**, `\n\n`-separated.
Corroborating, a *different* block in production-synced data already showed a note that is visibly
this merge's output — split mid-word across the `\n\n` joins. **The notes were never being deleted.
The server is exonerated for real this time, not just by reading it.**

**Root cause — the note was in the database and the UI could not address it.** Three dictionaries in
`EditExegesisActivityPage.swift` — `noteDrafts` (`:183`), `attributedNoteDrafts` (`:184`) and
`savedNoteMarkdownByHighlight` (`:185`) — are keyed by `highlightNoteKey`, i.e. `"location:length"`
(`:649-651`). A merge changes the span by definition, so every absorbed highlight's key is stale the
instant the merge lands. The UI looked under a key that no longer existed and reported no note.
Indistinguishable from deletion to the person using it. This is the same failure *class* as
`12668543338` sub-issue A, as the deep dive predicted.

**The fix.** Identity succession now happens where the client actually learns a merge occurred (the
create path in `applyStyle`): the absorbed spans' entries are dropped from all three dictionaries and
the merged row's note is written under the new span's key — into both draft maps as well as the saved
one, so the draft follows the server's concatenation instead of preserving a single pre-merge
fragment. The `TEMPORARY DIAGNOSTIC` added to make this decidable was removed; it had served.

**Deliberately the narrow fix, and recorded as such.** The keys are still derived from mutable
geometry, so the next thing that shifts an offset re-breaks this. The real design — one draft map
keyed by highlight id, the saved mirror deleted in favour of the entity store, and a single
`applyMerge` seam owning succession — needs the `EntityStore<Highlight>` that the spec's Phase 4
builds, and is scheduled there as task 4.8b. Tracked at `docs/features/highlighting/09` §C-b so it
cannot quietly become the architecture.
