# I BROKE IT

## Problem
In the leader **lesson Preview**, on the **exegesis** step, the preview renders correctly at first; after the user **backgrounds the app** (switches to another app) and **returns**, the exegesis preview is broken: the scripture text is **clipped at the top**, the `‹  Done  ›` highlight-navigation toolbar is stranded **mid-screen**, and there is a large **empty black area** below it (with leftover/stray text). This is a hybrid surface — the iPhone native `LessonPreviewModal` hosts a WKWebView that loads the **web** member lesson player, so the broken layout is web-rendered inside the iOS preview. "Fixed" looks like: after returning from the background, the exegesis preview re-measures and lays out exactly as it did before backgrounding (scripture not clipped, toolbar pinned to the real bottom, no empty void) — without the user having to tap the ↺ restart button.

## Reports (verbatim)
- (2026-07-25) "In preview (which is working great), I navigate to another app (Monday) and when I come back, this is the preview for the exegesis screen"

The layout is collapsed/misaligned — the toolbar (normally pinned to the bottom of the reader) sits mid-screen and the content area does not fill the WebView.

## Root cause
A stale-layout cascade inside WKWebView (and mobile Safari) on foreground, with nothing forcing a re-measure. `exegesis-step.vue` derives its top inset + top-fade mask from `--member-lesson-header` (`exegesis-step.vue:610,618,625`), a var published **only** by a `ResizeObserver` on the header (`member-lesson-header.vue:12-16`) that fires on box-size change. On iOS, backgrounding a WKWebView can invalidate resolved `dvh`/`vh` and `env(safe-area-inset-*)`; on resume WebKit re-lays-out but the ResizeObserver does not re-fire (header box unchanged), so the var resolves stale/collapsed → scripture clips at top, and the `100dvh` container height mismatches the real WebView bounds → the `bottom:0` `‹ Done ›` overlay strands mid-screen with empty space below. Nothing re-syncs on resume: no `visibilitychange`/`pageshow`/`resize` handler in the web player, and the native side has no `.active`/foreground branch (`MakeReadyApp.swift:60-68` handles only `.background`). Introduced by the dynamic-header change in commit `d140bc2` ("reserve the header's live height instead of a static 120px…"), which fixed initial clipping but left the resume-time staleness path open.
