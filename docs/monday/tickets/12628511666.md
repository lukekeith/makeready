# preview issue

## Problem
iPhone app, READ activity editor (EditReadActivityPage, program context — the preview header shows "test program"). The leader types text into an editable text block and taps **Preview**. The preview modal (LessonPreviewModal — a WKWebView rendering the member lesson at `/preview/lesson/{lessonId}/{step}`) shows the lesson **without** the newly typed text, while the editor still displays it. Mechanism: block text is deliberately persisted only when the user taps **Save** ("no per-keystroke round trip"), but the Preview button is always available and `openSlidePreview()` does not flush unsaved edits — so the server-rendered preview reflects the last-saved state. "Fixed" looks like: tapping Preview with unsaved edits first persists them (or the preview otherwise reflects them), so the preview always matches what the editor shows.

## Reports (verbatim)

## Root cause
`EditReadActivityPage.swift:799-803` + `1098-1118`: editable-block text converts from AttributedString to markdown and PATCHes to the server only inside `save()` (invoked solely by the header Save link), while `openSlidePreview()` presents the server-rendered member preview without first saving. With `hasSaved == false`, the preview necessarily shows stale content. Not a caching issue — the preview URL gets a fresh token per open.

## Verification
1. **Code-level proof:** `EditReadActivityPage.swift:799-803` (no flush before `showSlidePreview = true`); `:1098-1118` (text persisted only in `save()`); `:492-495` (Preview available while unsaved).
2. **Manual repro (simulator + local stack):** open a program → day → READ activity with a custom text block → type new text → WITHOUT tapping Save, tap Preview. Observed: the preview's read step lacks the new text. Tap ✕, tap Save, tap Preview again: text appears — confirming the save/preview race.
3. Fixed = with unsaved edits, tapping Preview shows the new text (and the header flips to "Done", since the fix saves first).
