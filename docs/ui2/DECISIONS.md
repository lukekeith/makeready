# UI 2.0 — Program-level Decision Register

Normative rulings that bind every screen spec and every later build suite. Screen-local
decisions live in the screen's own spec (`screens/<id>.md` §8); anything cross-screen lands
here as a dated `D#` row. Never renumber — only append.

## Decision register

| # | Date | Decision | Ruling |
|---|---|---|---|
| D1 | 2026-09-01 | Platform split | **Members stay on web.** iPhone 2.0 is the leader/admin app; the new member lesson-consumption UI ships on the web client. This upholds the activities suite's decided platform strategy (`docs/features/activities/08-open-questions.md` §12): the native iPhone pager is the leader's edit-in-place canvas and writes no member progress. |
| D2 | 2026-09-01 | Coexistence | **Parallel shell, hard cutover.** UI 2.0 gets its own screen tree, navigation shell, and design-system layer inside the same iPhone app target, behind a flag. Legacy stays untouched and shippable until cutover; no legacy UI elements blend into 2.0 screens and no 2.0 elements leak into legacy. Mechanics in `migration.md`. |
| D3 | 2026-09-01 | Leader-parity project | **Frozen — superseded by UI 2.0.** The remaining 13 screens in `docs/parity/manifest.md` are not ported; already-ported screens stay in production until their 2.0 replacements land. Do not run `/parity-screen` for new screens. |
| D4 | 2026-09-01 | Reference model | **YouVersion (the Bible App by Life.Church)** is the reference app for the lesson experience; the frame analyses in `docs/features/activities/` are adopted as-is. ("Bible.org" in earlier conversation was shorthand for it.) |
| D5 | 2026-09-01 | Figma is normative | Where a screen has a Figma source, Figma is the source of truth: the spec cites the node URL + a frozen snapshot (`screens/assets/<id>.png` + capture date) and carries a closed deviation list per build-spec REFERENCE.md §3c. Later Figma edits are a visible re-spec event (`/ui2-screen <id> <url>` re-ingests and diffs), never silent drift. Screens specced without Figma name their doc source and are flagged `no-figma`. |
| D6 | 2026-09-01 | Registry exhaustiveness | `design-system/registry.md` is the exhaustive component universe for UI 2.0. Every visual element in every screen spec resolves to a registry row; a build-spec suite's `05`/`06` component manifest is a closed subset of registry IDs, and rendering anything outside the cited rows is a defect (the notes-N14 rule hoisted to program level). |
| D7 | 2026-09-01 | Tokens over raw values | A screen spec uses token names from `design-system/tokens.md`, never raw values where a token exists. A raw value in Figma with no variable becomes either a new token row or a per-screen literal explicitly flagged in the spec. |
| D8 | 2026-09-01 | Screen identity | Screen ids are `<area>-<name>` kebab-case and stable for the program's life; they key the README tables, spec filenames, snapshot assets, screen-map nodes, and registry Consumed-by columns. |
| D9 | 2026-09-01 | Component sheet scope | The Figma component sheet (node `3632:4502`, https://www.figma.com/design/nVva9a2WvYmcWQo6zlHupO/Make-Ready-Mobile?node-id=3632-4502) is where the owner parks ALL components, but it is **not wholly normative — some entries exist only for Figma prototyping** (owner, 2026-09-01). A sheet component becomes normative only when a screen spec consumes it; the sheet's role is to enumerate a consumed component's designed states/variants and tokens. Never bulk-absorb the sheet into the registry. |
| D10 | 2026-09-03 | Component-level specs | **`/ui2-component` specs one component per run** from an owner-pasted Figma component/set link. An owner-designated set is normative (refining D9's "not wholly normative" — designation is the owner's act of pasting it). The contract lives at `design-system/components/C-###-<name>.md` and becomes the registry row's "Defined in" anchor (screen-spec §4 remains the anchor for rows defined by screen runs); Consumed-by may legitimately be empty until screens consume the row. |
| D11 | 2026-09-06 | Per-component preview build | **A specced component can be BUILT as a capturable preview before the app build exists.** `/ui2-component-build <C-###>` generates tokens from `tokens.md`, a SwiftUI view under `iphone/MakeReady/UI2Preview/`, a fixture under `capture/fixtures/ui2/`, and a `ViewRegistry` case — so the browser renders it beside its frozen Figma snapshot and diffs the two (Figma is the reference, Swift the twin). Preview code is wired into no screen, route or flag and commits the program to none of the decisions `migration.md` reserves for `ui2-shell`, which later promotes these files. Mechanics and binding rules in `preview-build.md`. |
